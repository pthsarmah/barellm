UEFI 2.11 Field Guide

This guide gives the parts of the UEFI specification that apply when your EFI application is not a bootloader for a different OS. Your application is the OS. The target is LLM inference on bare metal. You must allocate large buffers, read the weight files quickly, get a framebuffer, and take full control of the machine.

1Specification map — the parts to read and the parts to ignore

UEFI 2.11, full TOC · uefi.org/specs/UEFI/2.11

The specification has approximately 2,500 pages in 39 chapters and 18 appendices. Most of the content is for firmware implementers and driver writers. An EFI application that takes control of the machine needs only six chapters. These chapters give almost all of the necessary data:

4EFI System TableThe entry point signature, the System Table, and the configuration tables. The ACPI pointer is in the configuration tables.

You can ignore these parts for this project: the UEFI Driver Model (Chapter 11), all networking (Chapters 24–31), HII (Chapters 33–35), the EBC virtual machine (Chapter 22), and Redfish (Chapter 31). This protocol is important for multi-core inference (Section 10).

Changes from 2.10: UEFI 2.11 adds new hash and signature algorithms for Secure Boot, and makes the implementation guidance more clear. The application model is the same. Code written for the 2.8 interfaces and later operates without changes.

2The application lifecycle

§2.1.1–2.1.3 UEFI Images · §7.4 Image Services

Your binary is a PE32+ image with the subsystem type EFI_APPLICATION or OS-loader. The only difference between the two types is the subsystem field. An OS loader is an application that will call ExitBootServices(). The firmware loads the image from the EFI System Partition, applies the relocations, and calls the entry point. All boot services are available at this time.

SEC/PEI/DXEFirmware initialization (PI specification)
BDSThe boot manager selects BOOTX64.EFI
efi_main()Boot services: allocate RAM, load the weights, set the video mode
ExitBootServicesThis step is permanent
LLM runtimeYou control the CPU, the RAM, and the devices

The default boot path needs no configuration. The firmware runs \EFI\BOOT\BOOTX64.EFI from a FAT-formatted ESP on removable or fixed media (§3.5.1.1). For development, a FAT32 USB stick with this one file is a full installation. A QEMU/OVMF disk image with the same path is also sufficient.

EFI_STATUS EFIAPI efi_main(EFI_HANDLE ImageHandle, EFI_SYSTEM_TABLE *SystemTable);
// ImageHandle: the handle of your image (it has EFI_LOADED_IMAGE_PROTOCOL)
// SystemTable: the access point to all other services (§4)
// If you return from efi_main, the firmware unloads the app.
// After ExitBootServices, do not return.
Warning — the watchdog timer

Disable the watchdog timer immediately: BS->SetWatchdogTimer(0, 0, 0, NULL) (§7.5.1). The firmware starts a 5-minute watchdog timer before it launches a boot option. If your application does not call ExitBootServices() before the timer expires, the platform does a reset. This failure is easy to cause when you load weight files of many gigabytes.

3The x64 environment and the calling convention

§2.3.1 Data Types · §2.3.4 x64 Platforms

This is the machine state at your entry point (§2.3.4). This state is your runtime contract:

  • Long mode, 64-bit. Paging is on. The full UEFI memory map is identity-mapped (virtual address = physical address). Some regions can be without the W or X attributes.
  • One processor. Only the BSP operates. The application processors are stopped. You can start them (Section 10).
  • Interrupts are on, but only the firmware timer uses them. There are no interrupt services for your application. The selectors are flat. The firmware owns the GDT and the IDT.
  • Stack: a minimum of 128 KiB, with 16-byte alignment. The stack can be non-executable. Inference call chains are deep, and local variables can be large. Put all large data on the heap.
  • FPU/SSE: the x87 control word is 0x037F. MXCSR is 0x1F80 (all exceptions are masked). SSE is available. The AVX and AVX-512 state is not enabled. You must set CR4.OSXSAVE and XCR0 before you run an AVX matmul kernel (Section 10).

The calling convention

All UEFI interfaces use the Microsoft x64 ABI (§2.3.4.2). The arguments go in RCX, RDX, R8, and R9, with 32 bytes of shadow space. The stack has 16-byte alignment at the call. The return value goes in RAX. Thus you compile with -target x86_64-unknown-windows, or you mark the functions EFIAPI / __attribute__((ms_abi)). Do not mix this ABI with the System V ABI of a usual Linux toolchain. That error causes an immediate crash. At the handoff, RCX = ImageHandle and RDX = the System Table pointer.

Data types you must know (§2.3.1)

4The System Table

§4.3 EFI_SYSTEM_TABLE · §4.6 Configuration Tables

All services are available from the pointer in RDX. This is the layout (signature 0x5453595320494249, "IBI SYST"):

typedef struct {
  EFI_TABLE_HEADER                 Hdr;            // signature, revision, CRC32
  CHAR16                           *FirmwareVendor;
  UINT32                           FirmwareRevision;
  EFI_HANDLE                       ConsoleInHandle;
  EFI_SIMPLE_TEXT_INPUT_PROTOCOL   *ConIn;         // keyboard
  EFI_HANDLE                       ConsoleOutHandle;
  EFI_SIMPLE_TEXT_OUTPUT_PROTOCOL  *ConOut;        // text console
  EFI_HANDLE                       StandardErrorHandle;
  EFI_SIMPLE_TEXT_OUTPUT_PROTOCOL  *StdErr;
  EFI_RUNTIME_SERVICES             *RuntimeServices; // continues after ExitBootServices
  EFI_BOOT_SERVICES                *BootServices;    // stops at ExitBootServices
  UINTN                            NumberOfTableEntries;
  EFI_CONFIGURATION_TABLE          *ConfigurationTable; // GUID → table pointers
} EFI_SYSTEM_TABLE;

The configuration tables — your hardware inventory

The configuration table array (§4.6) is a list of vendor tables with GUID keys. For a bare-metal runtime, the most important entry is ACPI. Compare the GUIDs in the array. Keep the RSDP pointer before you call ExitBootServices(). Then parse the XSDT, the MADT (the CPU topology, the LAPIC, and the IOAPIC), and the HPET. This data shows you your CPU cores.

5Memory services

§7.2 Memory Allocation Services · Tables 7.5–7.6 (memory type usage)

Two allocators are available while boot services operate:

  • AllocatePages(Type, MemoryType, Pages, &PhysAddr) allocates 4-KiB pages. The Type parameter is AllocateAnyPages, AllocateMaxAddress (all memory below a limit), or AllocateAddress (an exact address). Use this allocator for the weights. Allocate the model buffer as pages, not as pool memory.
  • AllocatePool(MemoryType, Size, &Buffer) allocates bytes, with 8-byte alignment. Use it for metadata and small structures.

Allocate memory as EfiLoaderData. This is the usual type for applications. Applications must not allocate EfiReservedMemoryType, EfiMemoryMappedIO, or EfiUnacceptedMemoryType. The specification keeps the MemoryType values 0x80000000 and above for OS loaders. Give your model buffer a custom type from this range. Then the buffer is easy to find in the memory map after you take control.

The memory map

GetMemoryMap(&Size, Map, &MapKey, &DescSize, &DescVersion) returns an array of descriptors (the physical start, the page count, the type, and the attributes). Obey two rules that are not obvious. Rule 1: use the returned DescriptorSize to move through the array. Do not use sizeof(EFI_MEMORY_DESCRIPTOR), because the firmware can use a larger stride. Rule 2: the map changes each time you allocate memory. Your MapKey then becomes invalid. This rule causes the ExitBootServices procedure in Section 9.

Ownership after ExitBootServices() — what each region means for your runtime:

EfiConventionalMemoryFree RAM: most of the machine. Use it for the KV-cache, the activations, and the heap.
EfiLoaderCode / EfiLoaderDataYour image and your allocations (the weights). This memory is yours.
EfiBootServicesCode / DataThis memory becomes free after the exit. Do not use it again before you stop all use of firmware data. This includes the GDT and the IDT. Load your own tables first.
EfiACPIReclaimMemoryThe ACPI tables. Make this memory free only after you parse the tables.
EfiRuntimeServicesCode / DataIf you call the runtime services, keep this memory permanently. Do not touch it.
EfiACPINVSMemoryFirmware work RAM. Keep this memory permanently.
EfiReservedMemoryType / EfiMemoryMappedIO / EfiUnacceptedMemoryTypeThis is not RAM (or the memory is not accepted, on confidential-compute platforms). Do not allocate it. Do not map it as normal memory.
yours after the exit yours after you parse it keep do not touch
Note — memory size for LLM loads

The conventional memory is divided into many regions. One large contiguous block is not guaranteed. A 7B-parameter f16 model (approximately 14 GiB) possibly cannot come from one AllocatePages call on some firmware. There are two solutions. Solution 1: allocate the largest block in each region, and divide the model across the blocks. Solution 2: make your own page tables after the exit. Then the physical fragments become one flat virtual area.

6Protocols, handles, and events

§2.4 Protocols · §7.3 Protocol Handler Services · §7.1 Events & TPL

Each firmware function is a protocol: a structure of function pointers with a GUID name, installed on a handle. Three procedures find all of the protocols that an application needs:

  • LocateProtocol(&guid, NULL, &iface) gets one available instance. Use this call for GOP and for other protocols that have only one instance.
  • HandleProtocol(handle, &guid, &iface) gets an interface from a handle that you have. For example, your ImageHandle gives the Loaded Image protocol. The specification prefers OpenProtocol() with GET_PROTOCOL, but HandleProtocol is satisfactory and more simple for an application with a short life.
  • LocateHandleBuffer(ByProtocol, &guid, NULL, &count, &handles) lists all instances (all disks, or all filesystems). Then examine each handle.

Events and TPLs (§7.1) are the firmware model for callbacks, without interrupts for applications. There are four priority levels (TPL_APPLICATION 4 < TPL_CALLBACK 8 < TPL_NOTIFY 16). TPL_HIGH_LEVEL 31 is only for the firmware. Events supply the timer callbacks. You need almost none of this. Use WaitForEvent on ConIn->WaitForKey for a "push a key" pause. Use BS->Stall(microseconds) for delays. Do not use the other event functions, and do not build on them. After ExitBootServices(), all events stop.

7Load the model weights

§9 Loaded Image · §13.4 Simple File System · §13.5 EFI_FILE_PROTOCOL · §13.9 Block I/O

This is the standard procedure to read the GGUF file into RAM after your application starts:

// 1. Get your image data and the device that supplied it.
EFI_LOADED_IMAGE_PROTOCOL *li;
BS->HandleProtocol(ImageHandle, &LoadedImageGuid, (void**)&li);

// 2. Get the filesystem on that device (the ESP).
EFI_SIMPLE_FILE_SYSTEM_PROTOCOL *fs;   // GUID 964e5b22-6459-11d2-8e39-00a0c969723b
BS->HandleProtocol(li->DeviceHandle, &SfsGuid, (void**)&fs);

// 3. Open the root, then the file (paths use CHAR16 and backslashes).
EFI_FILE_PROTOCOL *root, *f;
fs->OpenVolume(fs, &root);
root->Open(root, &f, L"\\model\\weights.gguf", EFI_FILE_MODE_READ, 0);

// 4. Get the size with GetInfo(EFI_FILE_INFO). Then read blocks into the
//    AllocatePages buffer.
f->Read(f, &chunk, buf + off);         // loop; the firmware can limit each read
Warning — the 4-GiB limit

FAT is the only filesystem that the firmware must support (§13.3). The maximum FAT32 file size is 4 GiB minus 1 byte. Large models are larger than this limit. These are your options:

(a) Divide the weights into files of less than 4 GiB. Attach the parts together when you load them. This is the most simple option and operates on all platforms. (b) Use a raw GPT partition. Make a partition with your own type-GUID. Find its handle with EFI_BLOCK_IO_PROTOCOL (§13.9). Examine Media->LastBlock and the partition entries. Use ReadBlocks to read the weights directly into RAM. This is the fastest option and uses no filesystem. (c) Do not use an NTFS or ext4 driver. Such drivers are not standard.

Speed note: read the file in large blocks (tens of MiB) directly into the destination pages. Each call has a large overhead, and firmware storage stacks are slow. On NVMe, Block I/O usually reads hundreds of MB/s. Use this number when you calculate the time from cold boot to the first token.

8The console and the framebuffer

§12.3 Simple Text Input · §12.4 Simple Text Output · §12.9 Graphics Output Protocol

Text: ConOut->OutputString(ConOut, L"tokens/s: ...\r\n") writes UCS-2 text with CR+LF, and operates immediately. ConIn->ReadKeyStroke polls the keyboard. Use these two services for output and input while boot services operate. Both services stop at ExitBootServices().

Graphics: the Graphics Output Protocol (GUID 9042a9de-23dc-4a38-96fb-7aded080516a) continues to operate after you take control, because it gives you a plain linear framebuffer:

  • Mode->FrameBufferBase is the physical address of the pixels. You can write to this address directly, at all times.
  • Mode->Info->PixelFormat is usually PixelBlueGreenRedReserved8BitPerColor (BGRX, little-endian, 32-bit).
  • Mode->Info->PixelsPerScanLine is the true stride. It can be more than HorizontalResolution. If you use the width as the stride, the image becomes distorted. This is a frequent error.
  • Select a mode with QueryMode and SetMode before you exit boot services. You cannot change the mode after the exit.

For the LLM chat UI, do these steps. Read the GOP data. Set your mode. Record the base address, the stride, and the pixel format. Then draw your own text into the framebuffer. Include a bitmap font in your application, because the firmware fonts are not available after the exit. This is the full display driver.

9ExitBootServices — the final step

§7.4.6 ExitBootServices()

This is the exact sequence. The retry rule causes many errors:

// All firmware tasks must be complete at this point:
// the weights are loaded, the GOP mode is set, the ACPI RSDP is kept,
// and the watchdog timer is off.
for (;;) {
    st = BS->GetMemoryMap(&size, map, &key, &dsize, &dver);  // new map + key
    // Do NOT allocate between these two calls. An allocation makes the key invalid.
    st = BS->ExitBootServices(ImageHandle, key);
    if (st == EFI_SUCCESS) break;
    // EFI_INVALID_PARAMETER: a timer or event made an allocation. Try again.
    // After a failed attempt, call only GetMemoryMap and ExitBootServices.
}

Important detail: allocate the map buffer before the loop, and make the buffer larger than necessary. The specification gives this guidance, because the allocation itself increases the size of the map. After success:

  • gone  All boot services, all protocol interfaces, and all events stop. ConIn, ConOut, and StdErr stop (the fields become NULL). The firmware timer and the watchdog timer stop.
  • yours  You control each core, all conventional memory, all boot-services memory, the GOP framebuffer (as plain memory), and all interrupts.
  • remains  The runtime services table (§8) continues: GetTime, ResetSystem, the variable services (refer to the RT-properties table, §4.6.2), and SetVirtualAddressMap. If you keep the identity map for the runtime regions, SetVirtualAddressMap is not necessary. This procedure is recommended.

The memory map from the exit is your permanent inventory of the physical RAM. Keep it.

10After the firmware — the tasks for your runtime

§2.3.4 (state rules) · ACPI spec · Intel SDM (not in the UEFI specification; listed because the specification stops here)

The specification defines the environment only up to the handover. After the handover, your runtime must do these tasks, in this approximate sequence:

  1. The GDT and the IDT: load your own tables immediately. The firmware tables are in memory that you can release. Install the exception handlers first. A page-fault handler that writes to the framebuffer saves days of work.
  2. SIMD for the inference kernels: the firmware makes sure of only the SSE state. Use CPUID to find AVX2 or AVX-512. Set CR4.OSXSAVE. Then use XSETBV to set the x87, SSE, and AVX (and ZMM) bits in XCR0. If you do not do this step, each AVX instruction causes a #UD fault.
  3. Timers: the firmware timer is stopped. Calibrate the TSC (with CPUID leaf 0x15, or with the HPET from ACPI) to measure tokens/second and to do the scheduling.
  4. Multicore: parse the MADT to get the LAPIC IDs. Then send INIT–SIPI–SIPI to start the APs. An easier alternative: use the PI EFI_MP_SERVICES_PROTOCOL before the exit to hold the APs in your own loop. Then you keep the firmware AP configuration. Matrix multiplication needs all of the cores.
  5. Page tables (optional, but probable): make your own tables. They connect the physical RAM fragments into one flat virtual area for the model. They also permit 2-MiB and 1-GiB pages. Fewer TLB misses give a measurable speed increase for large-tensor reads.
  6. Cache and write-combining: when you own the page tables, map the GOP framebuffer as WC with the PAT. Direct UC writes are too slow for a chat UI.

11Secure Boot

§32 Secure Boot and Driver Signing

When Secure Boot is on, the firmware launches only images with a signature chain to a certificate in the db variable. For this project, do these steps. On development machines, set Secure Boot to OFF in the setup menu, or run OVMF without it. On hardware that you ship or keep, install your own PK, KEK, and db keys. Then sign the application (Authenticode on PE32+, §32.2). QEMU with the default OVMF build does not use Secure Boot. Do not use a signature from the Microsoft third-party CA. That path (shim) is for Linux distributions and gives no advantage here.

12Toolchain notes for this repository

edk2 checked out at edk/edk2 · headers under MdePkg/Include

The edk2 build system is not necessary. The edk2 headers alone give you each structure and GUID in this guide, equal to the specification (they include the EFI_2_110 revision defines). Two good configurations:

ApproachHowTrade-off
clang + lld, freestanding clang -target x86_64-unknown-windows -ffreestanding -fshort-wchar -mno-red-zone -I edk/edk2/MdePkg/Include ... then lld-link /subsystem:efi_application /entry:efi_main No dependencies, full control, and the correct ABI by default. Recommended for baremetallm.
GNU toolchain + gnu-efi gcc uses ms_abi wrappers. The build links a small crt0 and a relocation shim. objcopy converts the output. This operates, but the ABI wrapper layer adds complexity that clang does not need.

These flags are mandatory for each compiler: -fshort-wchar (for CHAR16 literals) and -mno-red-zone (firmware interrupts can overwrite the red zone). Do not let the compiler make code above baseline SSE before you enable XCR0. Use -mno-avx for the boot-path code. Test loop: qemu-system-x86_64 -M q35 -m 32G -cpu host -enable-kvm -drive if=pflash,format=raw,readonly=on,file=OVMF_CODE.fd ... with your application as \EFI\BOOT\BOOTX64.EFI in a FAT directory, passed with -drive format=raw,file=fat:rw:esp/.

13Boot checklist — from efi_main to the first token

  1. Disable the watchdog timer — SetWatchdogTimer(0,0,0,NULL). Five minutes is not sufficient to load 30 GiB of weights.
  2. Write a start message with ConOut. This shows that the ABI, the linking, and the load path are correct, before more difficult errors can occur.
  3. Keep the ACPI RSDP pointer from the configuration table array.
  4. Read the GOP modes and set one. Record FrameBufferBase, the stride, and the pixel format.
  5. Allocate the model buffer with AllocatePages. Use a custom memory type of 0x80000000 or above, so that the buffer is easy to find.
  6. Load the weights — divided files through the Simple File System, or a raw partition through Block I/O.
  7. (Optional) Hold the APs in your own mailbox loop, with the PI MP Services.
  8. Call GetMemoryMap, then ExitBootServices. Use the retry loop. Do not allocate memory between the two calls.
  9. Take control of the machine. Load the GDT, the IDT, and the exception handlers. Set XCR0 for AVX. Calibrate the TSC. Start or release the APs. Make the page tables.
  10. Run the inference. The console output is the pixels that you draw. The input comes from your own keyboard driver (PS/2 emulation or USB). The keyboard is the most difficult device after the exit.
